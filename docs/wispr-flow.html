01 Requirements & Scope

Core features

  • ✓ Real-time voice dictation, system-wide (not confined to one app)
  • ✓ LLM-based cleanup: grammar correction, tone matching, personal phrasing adaptation
  • ✓ Context-aware output formatting (an email reads like an email, a code comment reads like a code comment)
  • ✓ Cross-platform: macOS, Windows, iOS, Android
  • ✓ Privacy controls: Privacy Mode (zero data retention) and optional Private Cloud Sync

Functional requirements

  • Capture audio from the OS microphone layer regardless of which foreground app has focus, and inject formatted text back into that app's input field.
  • Detect the active application and relevant visible context so formatting adapts to destination (Slack vs. email vs. IDE).
  • Process speech through an LLM-based correction/formatting pass rather than emitting a raw ASR transcript.
  • Support enterprise trust requirements (SOC 2 Type II, HIPAA controls) for regulated customers (sourced: Baseten case study, Wispr Flow security FAQ).

Non-functional requirements

  • Low perceived latency: end-to-end pipeline p99 < 700ms is the company's own stated target, prioritized over median latency (sourced: Baseten case study — "we're optimizing the p99 experience for the p99 user").
  • High transcription accuracy across accents, microphones, and background noise (independently reported ~92–97% depending on mic/environment).
  • Strong data-handling guarantees given audio/screen-context is sent to third-party cloud infra.

Out of scope

  • ✕ Fully offline/on-device transcription — Flow is cloud-only by design (the opposite tradeoff from on-device competitors like Superwhisper).
  • ✕ Meeting/multi-speaker transcription (Otter's category, not Flow's) — Flow is single-speaker, real-time dictation.
  • ✕ A public developer API for third-party integration (inferred — not publicly confirmed).
💡 Interview Tip

The single most interesting design decision here is architectural, not ML: Flow deliberately does not stream a live ASR transcript. It buffers, lets the LLM "understand what you meant," and only then renders text — trading a few hundred ms of perceived latency for dramatically fewer correction/backspace cycles. Framing your whole answer around that one tradeoff is a strong way to structure a live interview response.

02 Capacity Estimation

Assumptions

Daily-active-user figure is estimated from public download/retention data, not officially disclosed — flagged below.

  • ~2.5M cumulative downloads, 70% 12-month retention → assume ~400K–600K monthly active users (inferred)
  • Assume ~15% of MAU are daily dictation users → ~60K–90K DAU (inferred)
  • Assume average 25 dictation sessions/user/day, ~15 seconds of audio per session (typical for short dictation bursts)
  • Audio encoded compactly for upload (~16kbps compressed speech-optimized codec assumed)

Throughput / bandwidth

75,000 DAU × 25 sessions/day × 15s audio × 16 kbps
= 75,000 × 25 × 15 × 16,000 bits ÷ 8 bits/byte
= 75,000 × 25 × 30,000 bytes
≈ 56.25 GB of audio uploaded per day

Takeaway: Per-session payloads are tiny (~30KB), so the system is optimized for request volume and tail latency, not raw bandwidth — this is a high-QPS, low-payload workload, closer to a chat API than a media-streaming service.

Daily data volume

56.25 GB audio (transient, discarded unless Cloud Sync is on)
+ formatted-text transcripts (~1KB/session avg)
  75,000 × 25 × 1KB ≈ 1.9 GB/day of durable transcript text (only for users with Private Cloud Sync on)

Takeaway: Because Privacy Mode/no-retention is a first-class option, durable storage volume is a small fraction of total traffic — most audio is processed and discarded, not archived (architecture confirmed by Wispr's own data controls page and privacy policy).

Storage sizing

Assume 30% of MAU opt into Private Cloud Sync, 90-day rolling retention
500,000 MAU × 30% × 1.9GB/75,000 users/day × 90 days
≈ 150,000 users × ~25KB/day × 90 days
≈ 340 GB of retained transcript+metadata storage

Takeaway: This is a modest storage footprint even at scale — text is cheap; the hard engineering problem here is latency and correctness, not data volume.

Read/write QPS

75,000 DAU × 25 sessions/day ÷ 86,400s/day ≈ 22 dictation-completion writes/sec average
Assume 8x peak-to-average ratio (dictation clusters around work hours across timezones)
≈ 175 peak writes/sec for the inference pipeline

Takeaway: Peak QPS is well within range of a single well-provisioned autoscaled GPU serving fleet — this maps directly to why Baseten's autoscaling (rather than fixed GPU reservation) was the stated infra choice (sourced: Baseten case study).

03 High-Level Architecture

Why this shape?
  • Client stays thin (capture + VAD + injection only) so the same core cloud pipeline serves four very different OS surfaces (Mac, Windows, iOS, Android) without duplicating the AI stack per platform.
  • Cloud-only inference is a deliberate tradeoff (not a limitation) — it's what makes context-aware LLM formatting possible at all, since on-device models couldn't match the fine-tuned Llama quality bar (sourced: Wispr's own product blog).
  • Storage is opt-in and decoupled from the hot path — the default path (no Cloud Sync) never touches durable storage at all, keeping the common case both fast and low-liability.

Request flow

  1. User speaks; OS-level overlay captures audio locally and runs basic voice-activity detection.
  2. On pause/completion, the buffered audio (plus lightweight active-app/context signal) is sent to the cloud pipeline.
  3. Baseten-hosted, fine-tuned Llama models (served via TensorRT-LLM engines, orchestrated through Baseten's Chains framework for the multi-step pipeline) transcribe and reformat the speech in one pass — not a live streaming transcript.
  4. The formatted text token stream returns to the client (Wispr reports 100+ tokens generated in <250ms).
  5. The client injects the finished text directly into the focused application's input field.
  6. If Private Cloud Sync is enabled, the transcript is written to encrypted storage; otherwise it's discarded immediately after the response is delivered.

🔑 Critical Design Detail

The retention model is the actual product differentiator here, not the schema shape. Wispr explicitly separates "Privacy Mode" (are we allowed to train on/store this at all) from "Cloud Sync" (do we persist transcripts for the user's own history) — Zero Data Retention is defined specifically as both being off simultaneously (sourced: Wispr Flow data controls page). Any credible data model for this product has to represent that as two independent flags, not one binary "save or don't."

06 Audio Capture & OS Integration

Flow runs as an OS-layer overlay rather than embedding inside individual apps — described in its own product writing as "a layer that runs across them all: email, Slack, Notion, iMessage, ChatGPT, etc." (sourced: Wispr Flow blog, "Designing a natural and useful voice interface").

OS Accessibility / Input Layer
Wispr Overlay Process
Focused App's Text Field
  • Local voice-activity detection (VAD) determines start/stop of a dictation turn before anything is sent to the cloud.
  • A persistent, low-attention UI element ("a small, persistent bar on the dock") signals recording state without being visually intrusive.
  • The overlay must integrate with OS-level accessibility/input APIs to inject text into an arbitrary focused field — this is the hardest cross-platform engineering problem in the whole system, not the ML.
Tradeoff

Building a true OS-level overlay (vs. a per-app plugin/extension model) means far more platform-specific engineering work, but it's what lets Flow work identically inside Slack, an IDE, or a native mobile app — a plugin-per-app model would never reach that breadth.

07 LLM Post-Processing Pipeline (Not Streaming ASR)

This is the architectural decision most worth interview time.

Audio
Speech Encoder
Fine-tuned Llamatranscribe + clean + format
Final Text

(no intermediate raw-transcript UI shown to user)

  • Traditional dictation tools stream a raw ASR transcript token-by-token, visibly correcting itself as you speak. Flow deliberately withholds output until the LLM pass completes, explicitly described as choosing to "wait, understand, and then write what you meant" rather than what was literally said (sourced: Wispr Flow blog).
  • This single pass handles transcription, grammar correction, tone-matching, and (over time) adaptation to a user's personal phrasing style together, rather than as separate pipeline stages (sourced: Wispr Flow blog).
Tradeoff

Buffer-then-format vs. stream-then-correct. Streaming feels more "live" but produces visibly messy intermediate text and more user-side correction. Flow's buffered approach adds a few hundred ms of perceived latency (justifying the aggressive p99 < 700ms target) in exchange for output that's usually correct on the first render.

08 Context-Aware Formatting

  • The client detects the active application and relevant visible content and passes that as context alongside the audio (sourced: research summary of Wispr's architecture).
  • The same underlying LLM pass uses that context to decide output shape: an email destination produces email-formatted prose, a code-editor destination produces a properly structured code comment.
Tradeoff

Sending screen/app-context metadata to the cloud (not just raw audio) increases what's "personal/sensitive" about each request — which is precisely why Privacy Mode / Zero Data Retention exists as a first-class, easily-toggled control rather than an afterthought.

10 Privacy Modes & Zero Data Retention

  • Privacy Mode: controls whether dictation data can be used to evaluate/train/improve AI models (by Wispr or any third party). Off by default for non-HIPAA users (sourced: Wispr Flow security/compliance FAQ).
  • Private Cloud Sync: controls whether transcripts are durably stored (encrypted at rest/in transit) vs. processed in real time and discarded after the request completes.
  • Zero Data Retention (ZDR) = Privacy Mode on and Cloud Sync off, simultaneously — no training use, no server-side storage at all.
  • Compliance posture: SOC 2 Type II certified, HIPAA controls available on all plans (sourced: Baseten case study, Wispr security FAQ).
💡 Interview Tip

This is a good place to demonstrate PM-level thinking, not just engineering: the retention model isn't just a technical toggle, it's a segmentation strategy — HIPAA/enterprise customers get privacy-by-default, prosumer users get convenience-by-default (searchable dictation history), and the same underlying architecture serves both without a separate deployment.

11 Cross-Platform Divergence (Android vs. iOS vs. Desktop)

  • Android: floating overlay/bubble sits above every app — a deliberate choice to avoid Android's fragmented keyboard-replacement ecosystem (sourced: Wispr Flow blog / research summary).
  • iOS: implemented closer to a keyboard-extension pattern, aligning with Apple's stricter platform conventions for system-wide input (sourced: research summary).
  • Desktop (Mac/Windows): full OS-level accessibility-layer integration, injecting text into essentially any focused field.
Tradeoff

A single "floating bubble" UI everywhere would be simplest to build, but iOS platform constraints make that pattern awkward there — so Flow accepts extra platform-specific engineering to respect each OS's conventions rather than forcing one UI paradigm across all four platforms.

Scaling & Caching

Cache hierarchy: Given the workload is short, unique, per-user audio, there's little to cache on the inference path itself (each request is novel speech) — the more relevant caching is at the model-serving layer: warm GPU model replicas kept ready via Baseten's autoscaling rather than cold-starting per request (inferred implementation detail; autoscaling behavior itself is sourced from the Baseten case study).

Hot-key mitigation: Not a classic hot-partition problem — traffic is naturally spread across millions of independent users/sessions rather than concentrated on a few keys. The closer analog is regional load concentration during business hours across timezones, addressed by autoscaling GPU capacity rather than data-layer sharding.

Sharding: Persisted transcript/account data would naturally shard by user_id/org_id given the access pattern established in Section 05 (inferred).

Multi-region: Wispr's infrastructure is described as supporting multi-region deployments for compliance and latency reasons (sourced: Baseten case study); primary inference is documented as running in AWS us-east-1, with other regions likely used for latency-sensitive or data-residency-constrained customers (inferred beyond the confirmed us-east-1 detail).

Quick Q&A

Why not stream ASR results like most dictation tools?

Streaming ASR shows visibly-wrong intermediate text; buffering lets the LLM correct for meaning before anything renders.

How do they hit sub-second latency with an LLM in the loop?

Self-hosted fine-tuned models on dedicated, autoscaled GPU infra (TensorRT-LLM via Baseten) instead of a general-purpose hosted API.

What happens to my audio?

Discarded after processing by default; only persisted (encrypted) if the user explicitly enables Private Cloud Sync.

Why is this cloud-only instead of on-device like some competitors?

The LLM-based formatting quality bar isn't achievable on-device today; cloud-only is a deliberate quality tradeoff, not an oversight.
